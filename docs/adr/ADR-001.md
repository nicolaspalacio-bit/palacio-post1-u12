# ADR-001: Capas simples para persistencia; el seam de notificacion ya cubre el proximo cambio conocido

## Estado
Aceptado — 2026-10-10

## Contexto
Tras integrar exitosamente los patrones de comportamiento Chain of Responsibility (validacion), Strategy (calculo) y Observer (notificacion) en el sistema de solicitudes de reembolso, corresponde resolver si la arquitectura global del proyecto debe migrar hacia una Arquitectura Hexagonal completa (definiendo puertos e interfaces intermedias desacopladas para todas las dependencias externas) o mantenerse en una arquitectura en capas simples.

El analisis del contexto del negocio arroja dos hechos determinantes:
1. No existe ningun plan de contingencia ni requerimiento a corto o mediano plazo para sustituir la base de datos relacional ni el framework Spring Data JPA.
2. El area de Contabilidad anuncio formalmente que durante el proximo trimestre se realizara una integracion con una API externa para el procesamiento bancario y pago de solicitudes aprobadas.

## Decision
Se decide mantener una arquitectura en capas simples para la persistencia:
`SolicitudReembolsoService` dependera directamente de `RepositorioSolicitudesJpa`, sin introducir una interfaz intermedia de puerto ni mappers de infraestructura adicionales. Introducir un puerto para persistencia en este momento constituiria una abstraccion especulativa prematura que viola el principio YAGNI (You Aren't Gonna Need It), anadiendo sobrecarga de mantenimiento sin ningun driver tecnologico real.

Por el contrario, para el subsistema de notificacion no se introduce ninguna modificacion arquitectonica adicional: la interfaz `ObservadorCambioEstado` ya actua como el seam (punto de extension) adecuado. Cuando llegue la fecha de integracion con la API bancaria de Contabilidad, bastara con actualizar la implementacion interna de `NotificadorContabilidad` (o registrar un nuevo adaptador HTTP como observador) sin alterar en lo absoluto el servicio de aplicacion ni los demas observadores (`NotificadorEmpleado` y `NotificadorAuditoria`).

## Alternativas Descartadas
1. **Migracion a Arquitectura Hexagonal pura y simetrica:**
   - Se evaluo crear una interfaz de puerto `RepositorioSolicitudes` en el dominio o la aplicacion y un adaptador JPA en infraestructura (`AdaptadorRepositorioSolicitudesJpa`).
   - Se descarto porque anadiria indirection, duplicacion de clases y conversion de tipos sin que exista ninguna probabilidad real de cambiar el motor de base de datos en los proximos tres anos, violando la regla de YAGNI y encareciendo el costo cognitivo innecesariamente.
2. **Reemplazo de la lista de observadores por Spring ApplicationEventPublisher:**
   - Se evaluo emitir eventos mediante el bus interno de Spring.
   - Se descarto porque una lista inyectada de tres observadores fijos ofrece trazabilidad directa en tiempo de compilacion, menor costo de depuracion y desacopla suficientemente a los consumidores sin requerir un bus de eventos reflexivo.

## Consecuencias
### Consecuencias Positivas:
- Se preserva la simplicidad cognitiva del modulo segun los principios KISS y YAGNI, evitando interfaces fantasmas y mapeos redundantes.
- El tiempo de compilacion, navegacion de codigo y depuracion se mantiene optimizado.
- El unico cambio de infraestructura con fecha confirmada (integracion externa de Contabilidad) queda perfectamente soportado por el patron Observer ya implementado.

### Consecuencias Negativas y Mitigacion:
- Si en un futuro imprevisto fuera indispensable cambiar el motor de base de datos, el puerto de persistencia debera ser introducido retroactivamente mediante refactorizacion. El equipo asume conscientemente esta decision tecnica calculada.
- Un revisor que espere simetria dogmatica entre capas (puertos obligatorios en todos los extremos) podria percibir una asimetria entre persistencia y notificacion, la cual queda formal y tecnicamente fundamentada en este ADR.
